# Workforce API implementation notes

Contract routes and envelope shapes in accounts-workforce-contract.md are retained.

- Employee POST: `branchId,name,userId? (or null),employmentType,rate,joinedOn`.
- Employee PATCH safe fields: `name,userId,leftOn,rate,employmentType,rateEffectiveFrom`. Branch transfer and joinedOn changes are not supported. `leftOn:null` reopens employment only if no affected payroll month is closed.
- Employee login links are editable only before the employee has any leave history. A changed `userId` (clear, replace, or assign to a previously unlinked employee) returns 409 after ANY PENDING/APPROVED/REJECTED leave. This applies to every editor including Owner, not just the linked beneficiary. Repeating the existing link and other safe edits remain allowed. This deliberately conservative, schema-free safeguard retains the historical beneficiary used by self-review checks and self-service history; approved records do not become a loophole after the pending queue empties. Employee PATCH and leave submission/review share the existing mutation transaction lock, so concurrent writes cannot slip between the history check and relink. If links had already been changed before this safeguard, the original beneficiary cannot be reconstructed reliably from requestedById for on-behalf requests; historical remediation/flexible relinking needs a separately approved immutable beneficiary snapshot migration.
- Rate/type changes REQUIRE `rateEffectiveFrom` explicitly, first day of a future calendar month in Asia/Kolkata. Changes are append-only, increasing effective dates; no overwriting an already scheduled rate. Any attendance/leave/finalized activity on or after that date blocks the change. Employee GET `rate` / `employmentType` / `rateEffectiveFrom` represent today's effective compensation (not a future scheduled rate). Additional `compensationHistory:[effectiveFrom,rate,employmentType]` is PAYROLL-only, so UI can show scheduled changes. Rates are INR decimal strings.
- `GET employees` is PAYROLL-only; attendance employees DTOs exclude rate/history and employment type. Leave DTO employees are only `id,name`.
- Leave submit-on-behalf requires LEAVE_APPROVAL or PAYROLL. LEAVE_SELF can submit only the employee linked to the current identity. Leave review requires LEAVE_APPROVAL. Own linked employee/requested-by actor cannot self-review (including Owner). Rejection does not require payType; approval requires PAID/UNPAID.
- Payroll rows include additional `rateSegments:[effectiveFrom,rate,employmentType,payableHalfUnits]` for exact historical rate audit. Stored snapshot rows always FINAL; no money is transferred. Finalization requires a completed calendar month in Asia/Kolkata and explicit single branchId. The API permits deliberately closing an empty branch/month run. The Payroll page deliberately requires at least one employee (>=1) and does not expose empty closures, to prevent accidental permanent onboarding blocks: a closed branch/month disallows adding or backdating employees into it.
- Dates are strict YYYY-MM-DD (1900–2199), month YYYY-MM, no future attendance; future leave requests remain allowed. All writable body fields are allowlisted; unknown fields rejected.
- All payrollSnapshots rows are final and expose branchId,employeeId,month,amount for P&L. No status column/filter required.
