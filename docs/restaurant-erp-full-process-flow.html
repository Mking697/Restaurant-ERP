Detailed Explanation — 27 cards, one per real flow

1. Order Capture - Branch POS

  • POS user selects table/takeaway, counter and same-branch sellable items, then confirms. This is the responsive POS screen, not a separate waiter app.
  • Branch/grant/session checks run server-side. A configured branch requires an open shift and accepted incoming handover before sale.

2. Recipe Builder — Define the Dish's Real Recipe (one-time setup)

  • Before anything can be sold, its recipe is saved once in Recipe Builder: the dish/Semi-FG name, branch, output unit (portion/kg/ltr/pcs), batch yield, and every ingredient row — each either a raw material OR an existing same-branch Semi-FG. The whole dish + recipe saves atomically in one go; saving a recipe never touches stock.
  • Example: Butter Chicken's recipe = 0.1kg Gravy (Semi-FG) + 0.25kg Chicken per portion. Gravy's own recipe = 0.3kg Tomato + 0.3kg Butter per 1kg produced. A cycle (Gravy needing itself, directly or through another Semi-FG) is rejected at save time.

3. Semi-FG Production — Real Prepared Stock, Not Virtual

  • A Semi-FG only becomes real, sellable stock after it is actually PRODUCED on the Production panel — pick the Semi-FG and an output quantity, Record production. This is the ONLY action that credits real prepared stock in Postgres (semi_fg_stock).
  • Production consumes the Semi-FG's OWN direct raw materials (and any nested Semi-FG) exactly once, then credits the produced quantity. Each production is idempotent and its history is immutable — a retried request never double-deducts or double-credits.
  • Example: Recording 1kg of Gravy production consumes 0.3kg Tomato + 0.3kg Butter from real branch inventory right then, and credits 1kg to Gravy's own Semi-FG stock — before this, Gravy's sellable stock is 0.

4. Stock Check Engine — Direct Raw + Produced Semi-FG Only

  • On Confirm Order, the system checks and atomically deducts ONLY the direct raw materials and any already-PRODUCED Semi-FG stock each line needs — it never walks back into a Semi-FG's own embedded raw ingredients a second time (no recursive/virtual deduction).
  • If a dish needs a Semi-FG that hasn't been produced yet, or produced stock is short, the WHOLE order is rejected with a clear message — never a partial sale, and the cashier is told to produce it first.
  • Example: Butter Chicken needs 0.1kg Gravy + 0.25kg Chicken per plate. Selling 10 plates needs 1kg Gravy stock (from Step 3's production) + 2.5kg Chicken — Gravy's own Tomato/Butter is never touched again at sale time.

5. Kitchen KOT + Semi-FG Stock Alert

  • Confirmed sale returns a KOT view containing item names and quantities without prices, alongside the billing receipt. Separate kitchen-device delivery or automatic printing is not claimed.
  • Use prepared-stock preview to identify Semi-FG shortage and record another batch. A scheduled automatic low-stock message is not established.

6. Central + Branch Warehouse

  • The Owner sets up one Central warehouse (bulk stock) and each branch gets its own local warehouse.
  • Example: Central dispatches 50 kg Chicken to Branch B2 — this is a paper record only; B2's actual stock has not changed yet.

7. Receive = the Real Stock Move

  • Dispatch is just a record; branch inventory only changes when the branch confirms Receive.
  • Example: B2 receives 48 kg (out of 50 dispatched) — B2's inventory now gets +48 kg, and the 2 kg shortfall is recorded separately, never hidden.

8. Auto Stock Deduction + Low Stock Alert

  • Sale atomically deducts direct raw + already-produced Semi-FG stock. Any shortage rejects the whole sale; embedded Semi-FG raw is not consumed again.
  • Inventory min/max badges identify configured raw-stock limits. GRN Quality PASS/PARTIAL now really posts the passed quantity into this same Inventory table (see card 23) — the earlier known gap is closed.

9. POS Receipt — 2 Billing Counters

  • Each order records Counter 1 or Counter 2. Both use the same branch stock and shift rules; this is counter attribution, not a separate independent cash drawer ledger.
  • Successful confirmation returns the real receipt and KOT. Displayed sales are today-scoped; latest 200 rows are listed while totals cover all completed sales in the same scope.

10. GST Invoice — CGST/SGST/IGST Auto-Split

  • When branch and company GST state codes are configured, billing computes GST and splits CGST/SGST or IGST. Unconfigured orders are billed without GST and excluded separately by the export.
  • Illustration only: taxable 300 at 5% yields 15 tax; intra-state split is 7.50 + 7.50. Tax configuration and filing review remain the business responsibility.

11. Multi-Currency — NRI / Export Billing

  • Optional non-INR tender requires an Owner-configured exchange rate. The sale snapshots that rate and payment amount; the invoice amount stays in INR.
  • Example: INR 363.20 / 84.50 gives USD 4.30 payment convenience. Later FX edits do not rewrite the saved sale.

12. Accounts -> GSTR Export - Actual Eligible Sales

  • GSTR Export is a tab inside Accounts, no separate sidebar item. Owner or a branch-scoped user explicitly granted OFFICIAL_SALES_REPORTS can view/download its HSN summary. POS_CASHIER alone is insufficient.
  • Owner-only operational orders remain included with every other eligible completed order. Missing GST setup is reported as excluded; privacy never changes tax/invoice totals. CSV is a summary for review, not a claim that filing has occurred.

13. WhatsApp Thank You Message

  • Optional customer phone triggers a best-effort ChatXFlow Thank You text after the order commits. Provider failure never rolls back the real sale; sent/failed outcome is displayed.
  • The text contains order number, total and branch. There is no generated invoice-link delivery implied, and a previously sent message cannot be recalled by later privacy changes.

14. WhatsApp Offer Campaign

  • Offer preview and send audience derive distinct customer contacts from actual past orders. Non-Owners exclude contacts found only on Owner-only orders; Owner sees the full scoped audience.
  • A send is an external side effect, separate from saving an order. This chart update sends no messages and creates no business records.

15. Shift Setup + Start - Local QA, Not Deployed

  • Owner can configure any branch; Branch Admin with SHIFT_MANAGEMENT only their own. Set 1-12 contiguous IST windows covering 24 hours; one same-start/end window covers a full day.
  • Start Shift selects the current window. A branch has one open run. A branch not configured retains legacy POS behavior; setup is required before real shift closing. Old definitions/history survive later edits.

16. Blind Count -> End Shift -> Next Run

  • Cashier or authorized operational user enters note/coin counts without expected cash. Manual End Shift saves the count and shortage/excess, ends the old run, opens its cyclic successor and creates a PENDING handover atomically.
  • Expected closing cash = accepted incoming counted cash + this run CASH sales. Example: received 500, new cash sales 300, count 790 -> expected 800 and shortage 10. The next shift receives physical 790.
  • Card/UPI/Other are current-run receipt summaries only, never accumulated bank transfers. Initial cash float and safe withdrawals are not modeled.

17. Accept Handover -> Repeat the Cycle

  • The incoming first authorized cashier sees actual Cash/Card/UPI/Other totals and must Accept Handover. POS and another closing remain blocked until acceptance; then the same operational cycle repeats.
  • A one-window branch opens a NEW run of the same window, never reuses the ended run ID. Time reminders are settings-only; time alone never closes a shift. Unknown closing outcome is not blindly retried.

18. Owner-only Privacy - Local QA, Not Deployed

  • Only Owner can mark a saved order Owner-only or restore staff visibility, with a reason. Visibility change and its audit entry commit together; repeated same-state requests do not create duplicate audit events.
  • Example: two 500 orders -> Owner sees actual 1000 / staff-visible 500 / private 500. Staff API/table returns only the visible order and labels 500 as access-filtered, not actual total.

19. Actual Accounting Is Never Filtered by Privacy

  • Private operational visibility never deletes sales, changes invoices/GST, reverses stock or reduces actual cash reconciliation. Official Accounts GSTR remains unfiltered under its separate grant.
  • Cash custodians and authorized official readers may infer actual aggregate amounts. Past views, printouts, screenshots, downloads and sent receipts cannot be revoked. Existing sample dashboards/reports are not live privacy-aware sales totals.

20. Real Accounts + Workforce Modules

  • Accounts stores categorized expenses and final payroll costs. Attendance, approved leave, employee rate history and payroll finalization have real DB-backed paths; branch and module grants control access.
  • Payroll uses actual calendar days, no weekly-off concept. Only approved paid ON_ROLL leave is paid; OFF_ROLL earns worked days. Missing attendance blocks finalization. P&L does not invent sales/COGS/net profit when those sources are unconnected.

22. Tasks — Recurring + Delegation (Demo UI)

  • Recurring Task (fixed D/W/15D/M/Q/Y frequency) and Delegate Task (one-time, assignee + due date) both open a dialog and add a row to the on-screen list; Checklist is the same engine as Recurring, not a separate system.
  • Mark Done blocks submission for a one-time task with no attachment, optional for recurring. This whole module runs on page-local mock data today — no Postgres table backs it yet, same gap flagged across the project.

23. Purchase & GRN — Indent to Quality Check (Demo UI)

  • Raise Indent (raw material + branch + qty) -> manager Approve/Reject -> Purchase Order 3-step (Bought / Bill / Material Received) -> GRN Quality Check PASS/FAIL/PARTIAL, with a fail/partial return + refund note.
  • RESOLVED: GRN Quality PASS or PARTIAL now calls a real POST /api/inventory/receive and atomically increases the real inventory_stock row for that branch+material (creates it on first receipt). Verified live: 20kg create, +5.5kg second receipt -> 25.5kg, confirmed by re-reading the real Inventory table over HTTP. FAIL/PARTIAL's failed-qty vendor return + Accounts refund entry is still demo-only.

24. Users, Branches & Access — Real, DB-backed

  • Create User sets role + branch + moduleAccess grants; grants decide which nav items and API actions a user can reach, including gating Shift configuration to Owner/Branch Admin. Module Grants also gates Shift configuration (Owner/Branch Admin only).
  • Branch Setup covers add/edit branches and the Clone-Branch-Wizard button in the UI; the actual multi-step clone flow (copy menu/BOM/checklists into a new branch) is UI-only today, not a backend job yet.

25. Dashboard, Reports & MIS Leaderboard (Demo UI)

  • Owner Dashboard KPI cards, the 6-report picker (sales trend, MIS scorecard, food cost, inventory variance, cash reconciliation, aggregator recon) and the MIS Leaderboard all render from src/lib/mock-data.ts today, not live branch totals.
  • The branch selector in the topbar does not yet filter this data. Treat every chart/number on these three screens as illustrative, not an accounting source — Accounts/GSTR/Inventory/POS are the real numbers elsewhere in this chart.

26. Attendance + Leave — Real DB-backed

  • Daily attendance is marked per employee. Leave Apply goes to a DIFFERENT manager (never the same person who can approve their own linked employee or their own request) for Approve/Reject; only approved paid ON_ROLL leave is paid, OFF_ROLL earns worked days only.
  • There is no weekly-off concept in this system — payroll uses actual calendar days (28/29/30/31), not a fixed working-days assumption.

27. Payroll Finalize — Immutable, Blocks on Missing Data

  • Payroll uses accumulated historical rate segments and one-paise rounding; future leave cannot become preview pay and pending leaves stay excluded. Missing attendance for any day in the period blocks finalization — no silent assumption.
  • Once finalized, a payroll run is immutable (same convention as Semi-FG production history) — a correction needs an explicit new entry, not an edit of the old one.
